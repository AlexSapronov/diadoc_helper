# ЭДО Контроль: отслеживание приглашений Диадока

Отдельное веб-приложение для Ubuntu VPS. Первоначальный MVP: входящие/исходящие приглашения, группы контрагентов в **самом Диадоке**, уведомления, предзаполненные письма, несколько собственных ящиков в одной учётной записи. Интерфейс на русском, рассчитан прежде всего на десктоп.

## Что реализовано

- Получение доступных организаций `GetMyOrganizations`; явное включение нужных ящиков.
- Синхронизация контрагентов `GetCounteragents (V3)` по статусам с пагинацией, групп `GetCounteragentGroups` с пагинацией.
- Поиск адресата по ИНН и КПП `GetOrganizationsByInnKpp`. Если найдено несколько ящиков, оператор выбирает нужный. **Отправка только по ИНН без подтверждённого ящика в MVP запрещена** ради исключения ошибочных приглашений филиалам.
- Отправка приглашения `AcquireCounteragent (V3)`; проверка результата `AcquireCounteragentResult (V3)`; выбор целевой группы **до отправки**.
- Принятие обычного входящего приглашения тем же `AcquireCounteragent (V3)` с **обязательным** выбором группы.
- После появления состояния `IsMyCounteragent` выполняется `AddCounteragentToGroup`, при ошибке назначение повторяется. Обязательность группы применяется как в интерфейсе, так и на сервере. Группа «По умолчанию» запрещена в формах назначения.
- Уведомление о принятом исходящем приглашении с кнопкой `mailto:`. В форме принятия входящего приглашения есть такая же кнопка. Email-получатели хранятся индивидуально для **каждой** нашей организации. Кнопка открывает локальный почтовый клиент, но не отправляет письмо без участия сотрудника.
- История действий, список ожиданий/ошибок, ручная синхронизация, фоновая синхронизация (по умолчанию 180 секунд).
- Локальный пароль, подписанная сессия, CSRF, хранение refresh-токена в зашифрованном виде в БД, сохранение обновлённого refresh-токена после каждого обмена.
- Локальный SQLite-файл с постоянным томом Docker. Для небольшого внутреннего приложения достаточно; при расширении до многопользовательской системы можно перейти на PostgreSQL.

## Важные ограничения

1. Приложение использует **одну сервисную учётную запись Диадока**, которая должна быть сотрудником с нужными правами во всех подключаемых ящиках. Для организаций, не доступных этой учётной записи, потребуется добавить ещё один независимый OAuth-профиль: этот MVP его пока не поддерживает.
2. Нельзя гарантировать обязательное назначение группы для приглашений, принятых в **обычном веб-интерфейсе Диадока**, через другую интеграцию или автоматически по настройке `Sociability=AllOrganizations`. Новые связи с группой «По умолчанию» отображаются как требующие внимания; доступно ручное назначение группы в таблице.
3. Входящие приглашения с вложением, **требующим ответной электронной подписи**, нельзя принять через взаимный вызов `AcquireCounteragent`; для этого требуется подписание вложенного документа методом `PostMessagePatch (V4)` или через Диадок. Подписание в этом MVP **не реализовано**. В случае невозможности принятия проверяйте вложение в Диадоке.
4. Токен и права должны разрешать работу с контрагентами (`CanManageCounteragents`), иначе часть методов вернёт 403. API может требовать отдельной коммерческой подписки, отсутствие которой возвращает 402.
5. Состояние «отправлено» и «принято» определяется фактическими ответами Диадока. Ошибки во время отправки **не приводят к автоматической повторной отправке**, чтобы избежать дублей: сначала проверьте статус вручную. Назначения групп повторяются автоматически.
6. Уведомления о принятии создаются при наблюдении перехода исходящего приглашения в `IsMyCounteragent` или при подтверждении исходящего приглашения, созданного в нашем приложении. Исторические приглашения, которые были приняты до первого запуска приложения, не создают «новых» уведомлений. Для продвинутого аудита событий можно позже добавить `GetCounteragentEvents (V1)`.
7. **Не проверено с настоящим аккаунтом Контур.Диадок и реальными приглашениями.** Есть локальные тесты с имитацией API, перед использованием с контрагентами требуется проверка на тестовой площадке.

## Подготовка доступа

1. Подать заявку на интеграцию Диадока и получить `client_id`, `client_secret`: <https://developer.kontur.ru/doc/diadoc-api/authentication.html>.
2. В Кабинете интегратора выпустить `refresh_token` для сервисной учётной записи, имеющей доступ ко всем нужным ящикам. Не использовать личную учётку сотрудника, если возможно.
3. Для тестовой площадки использовать отдельные тестовые ящики и `DIA_API_ENV=staging`. Не смешивать тестовые и промышленные идентификаторы.

## Установка в Ubuntu VPS

```bash
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-plugin
sudo mkdir -p /opt/edo-control
# Скопируйте файлы проекта в /opt/edo-control (например, scp или git clone).
cd /opt/edo-control
cp .env.example .env
chmod 600 .env
mkdir -p data
# Создайте хеш пароля (это интерактивная команда):
docker compose run --rm --no-deps edo-control python -m app.security
# Создайте ключ шифрования (одной строкой):
docker compose run --rm --no-deps edo-control python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
# Создайте ключ сессий (одной строкой):
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Вставьте значения в `.env`: `APP_PASSWORD_HASH`, `TOKEN_ENCRYPTION_KEY`, `APP_SESSION_SECRET`, `DIA_CLIENT_ID`, `DIA_CLIENT_SECRET`, `DIA_REFRESH_TOKEN`. Затем:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 edo-control
```

В приложении откройте **«Организации» → «Получить из Диадока»**, включите нужные ящики, внесите email-получателей для каждого и нажмите **«Синхронизировать»**. Пока группы не синхронизированы, приглашения отправить нельзя.

По умолчанию приложение доступно **только локально на VPS** по `http://127.0.0.1:8010`. Не открывайте порт 8010 напрямую в интернете. Для удалённого использования настройте существующий Nginx с HTTPS, например для `edo.example.ru`:

```nginx
server {
    listen 443 ssl;
    server_name edo.example.ru;
    # Укажите реальные пути к сертификату и приватному ключу
    ssl_certificate /etc/letsencrypt/live/edo.example.ru/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/edo.example.ru/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8010;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto https;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_read_timeout 90s;
    }
}
```

Здесь показан **только пример** HTTPS-прокси, не полная конфигурация выпуска сертификата. Используйте рабочие DNS и сертификаты. Для локальной проверки по HTTP временно установите `SESSION_HTTPS_ONLY=false`, **не оставляйте это значение на публичном сервере**.

## Резервное копирование

Остановите контейнер или используйте консистентный SQLite backup API; не копируйте файл базы «как есть» при активных записях. Сохраняйте `data/edo.sqlite3`, `.env` и **особенно `TOKEN_ENCRYPTION_KEY`** в защищённом месте. Потеря ключа сделает сохранённый refresh-токен нечитаемым. `.env` и базу нельзя публиковать в Git.
