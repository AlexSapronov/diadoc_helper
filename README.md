# ЭДО Контроль · трекер приглашений Контур.Диадока

Отдельное внутреннее веб-приложение для Ubuntu VPS. Позволяет работать с входящими/исходящими приглашениями для нескольких собственных организаций. При каждом приглашении оператор **обязательно выбирает существующую группу контрагентов Диадока**, а приложение назначает её после установления партнёрских отношений.

## Группы и подразделения Диадока

В Диадоке **группы контрагентов** и **подразделения** являются разными сущностями. Группа определяет доступные контрагенту подразделения (в которые он может отправлять документы), но не гарантирует автоматическое перемещение каждого документа в этот отдел. Ваша структура групп **уже настроена в Диадоке**: приложение получает её через `GetCounteragentGroups`, показывает названия без переименования и сохраняет конкретный `CounteragentGroupId` выбранной группы. Связи между группами и подразделениями остаются в ведении администраторов Диадока.

**Приложение никогда не вызывает `CreateCounteragentGroup`, `UpdateCounteragentGroup` или `DeleteCounteragentGroup`.** Не допускает выбора группы «По умолчанию» при отправке и принятии приглашения, чтобы пользователь выбирал осознанно.

Если группе нужно изменить разрешённые подразделения, это следует сделать в самом Диадоке. Выбор группы в нашем приложении не является выбором подразделения-отправителя (`myDepartmentId`), поэтому приглашение отправляется от ящика организации без указания отдельного подразделения отправителя.

## Возможности

- Получение собственных ящиков через `GetMyOrganizations` и их выбор для работы.
- Синхронизация **уже существующих групп контрагентов** для каждого ящика (`GetCounteragentGroups`), без добавления/редактирования/удаления групп.
- Отслеживание входящих, исходящих, принятых и отклонённых приглашений (`GetCounteragents V3`) с периодическим опросом раз в 180 секунд по умолчанию.
- Отправка приглашения (`AcquireCounteragent V3`) с **обязательным выбором группы**. Для адресата используется конкретный найденный ящик из поиска по ИНН.
- Принятие входящего приглашения с **обязательным выбором группы**, в том числе проверка на сервере. Приглашения с вложением, требующим подписания КЭП, необходимо обрабатывать непосредственно в Диадоке: этот MVP не подписывает такие документы.
- При изменении статуса на `IsMyCounteragent` назначение выбранной группы через `AddCounteragentToGroup`. При временной ошибке назначение повторяется, **но приглашение повторно не отправляется**.
- Возможность вручную изменить группу у уже подключённого контрагента, в том числе у контрагентов, подключённых вне приложения.
- Уведомления о принятии исходящих приглашений и кнопки `mailto:` с заранее заполненными адресатами, темой и текстом `Новый контрагент в ЭДО <наша организация> - <контрагент> - <ИНН>`; списки адресатов настраиваются отдельно для каждого собственного ящика.
- История операций, ручная синхронизация, пароль администратора, подписанная сессия, CSRF-защита, шифрование refresh-токена и SQLite в постоянном томе.

## Права и ограничения

- Один сервисный OAuth-профиль Диадока должен иметь доступ ко всем собственным ящикам. Независимые учётные записи на разные организации в текущем MVP не поддерживаются.
- Необходимы разрешения на управление контрагентами; в зависимости от API-метода и настроек ящика могут потребоваться права администратора и оплаченная API-подписка.
- Если контрагент принят в обычном интерфейсе Диадока или другая интеграция обошла наш процесс, приложение не может запретить такое действие. Новые связи, оставшиеся в группе «По умолчанию», будут отмечены для ручного назначения.
- Если выбранную группу удалили в Диадоке после отправки приглашения, приложение **не создаст новую** и **не назначит группу «По умолчанию»**. Оно сохранит ошибку назначения; сотруднику надо выбрать действующую группу.
- Группа Диадока может разрешать отправку документов сразу в несколько подразделений. Это не равнозначно адресации документа конкретному подразделению.
- Тесты используют имитацию API; до запуска с реальными контрагентами нужно проверить сценарии с тестовыми ящиками.

## Доступ к Диадоку

Получите `DIA_CLIENT_ID`, `DIA_CLIENT_SECRET` и `DIA_REFRESH_TOKEN` через [Кабинет интегратора](https://developer.kontur.ru/doc/diadoc-api/authentication.html). Записывайте секреты **только в `.env` внутреннего сервера**. Не публикуйте их в Git и не присылайте в чат. При проверке на тестовой площадке используйте `DIA_API_ENV=staging` и отдельные тестовые ящики.

## Развёртывание на внутреннем Ubuntu VPS

```bash
sudo apt-get update
sudo apt-get install -y git docker.io docker-compose-plugin
sudo mkdir -p /opt/diadoc_helper
sudo chown "$USER":"$USER" /opt/diadoc_helper
git clone https://github.com/AlexSapronov/diadoc_helper.git /opt/diadoc_helper
cd /opt/diadoc_helper
cp .env.example .env
chmod 600 .env
mkdir -p data
# Создаёт хеш пароля администратора (интерактивно):
docker compose run --rm --no-deps edo-control python -m app.security
# Ключ шифрования OAuth-токена:
docker compose run --rm --no-deps edo-control python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
# Секрет сессии:
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

Внесите результаты в `.env`: `APP_PASSWORD_HASH`, `TOKEN_ENCRYPTION_KEY`, `APP_SESSION_SECRET`, а также `DIA_CLIENT_ID`, `DIA_CLIENT_SECRET`, `DIA_REFRESH_TOKEN`. Стандартный логин: `admin`.

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 edo-control
```

Контейнер слушает только `127.0.0.1:8010`. Для доступа сотрудников используйте **внутреннее доменное имя и HTTPS** через Nginx/Caddy, либо VPN с корректно настроенным TLS. Не публикуйте `8010` в интернет. `SESSION_HTTPS_ONLY=true` оставьте для работы по HTTPS, при локальной диагностике по HTTP его можно временно отключить.

После авторизации: «Организации» → «Получить из Диадока» → включить нужные ящики → настроить получателей уведомлений → «Синхронизировать». Группы каждого ящика загрузятся из Диадока и станут доступны в формах приглашений.

### Обновление и резервная копия

```bash
cd /opt/diadoc_helper
git pull --ff-only origin main
docker compose up -d --build
```

Перед обновлением сохраните `data/` и `.env` в защищённое хранилище. SQLite копируйте с остановленным контейнером либо через SQLite Backup API. Не теряйте `TOKEN_ENCRYPTION_KEY`, иначе зашифрованный refresh-токен станет недоступен. Старые вспомогательные таблицы подразделений в БД не изменяются, но новая логика работает непосредственно с уже существующими группами.
